# Full-App Scope Decision Log — 2026-09-26 to 2026-09-27

## Human-approved direction

1. Replace the earlier mock-only implementation direction with a full React, Express, PostgreSQL, and Prisma application build.
2. Keep the core recommendation workflow available without login.
3. Use browser `sessionStorage` for current recommendation conditions and rejected menu-item IDs; keep the recommendation API stateless.
4. Use a single `User` model with `USER` and `ADMIN` roles.
5. Use email/password authentication, Argon2id password hashes, and a JWT stored in an HTTP-only cookie with a 7-day lifetime.
6. Create the initial administrator through a seed script using environment-provided credentials; do not expose public admin registration.
7. Allow administrators to manage zones, food types, tastes, restaurants, and menu items.
8. Soft-delete restaurants and menu items with `deletedAt`; normal admin flows do not permanently delete them.
9. Store catalog mutation audit events separately from legal traffic logs, with sanitized `before` and `after` snapshots and request IDs.
10. Allow registered users to save menu-item favorites, one default recommendation preference set, and history containing only menu items explicitly selected.
11. Do not persist allergies, food exclusions, rejected menu-item IDs, displayed shortlists, or full recommendation-session conditions.
12. Use manual `Zone` records instead of latitude/longitude or stored GPS.
13. Use Cloudflare Pages for the Vite React web application because it is static, has no runtime cold start, has a generous free tier for static hosting, supports team Git workflows, and fits the approved Cloudflare R2 image-storage direction.
14. Use Koyeb Serverless Postgres for the approved production database after the production deployment gate is passed. Keep Prisma migrations and application queries standard PostgreSQL so the database can move to Neon or another provider if production quota or reliability becomes insufficient.
15. Use Koyeb for the Express API. Keep the API stateless, deploy it reproducibly from Git or a container, expose a health endpoint, use environment variables for configuration, and do not depend on local disk persistence.
16. Use Cloudflare R2 Standard for restaurant and menu-item images. Store only generated object keys and delivered URLs in PostgreSQL, require administrator authorization for uploads, and validate file type and size at the API boundary.
17. Treat email as the account login identifier without verifying ownership in the first full-app pass. Registration accepts a syntactically valid unique email and password; do not add verification tokens, verification emails, or verification endpoints yet.
18. Delete accounts physically when account deletion is approved. User deletion cascades favorites, saved preferences, and selected-menu history; catalog audit logs keep their event data but set `actorId` to `null`.
19. Limit account email access to the account owner and authentication flow. Catalog administrators do not receive user email lists in the first full-app pass; future support access requires separate role, permission, endpoint, and audit decisions.
20. Process registered-account data only for optional account features: login, authentication, saved menu-item favorites, saved default recommendation preferences, and selected-menu history. Anonymous F1–F7 remains available without an account; do not use account data for advertising, unrelated profiling, or unrelated third-party disclosure.
21. Record selected-menu history automatically only for logged-in users when they explicitly select a menu item. Anonymous users do not write history to PostgreSQL. Users can clear history, account deletion cascades history, and no separate history opt-in toggle is added in the first full-app pass.
22. Retain application audit logs for protected catalog mutations for 180 days, then delete them through scheduled maintenance or a manual admin maintenance command. This audit-log retention is separate from any future Computer Crime Act traffic-log requirement.
23. Allow only `ADMIN` users to view application audit logs. Audit responses may include `actorId` but not actor email, and viewing audit logs does not create a nested audit event.
24. Keep soft-deleted menu items visible in favorites and selected-menu history with an unavailable status. Users can remove favorites; public catalog and recommendation flows exclude soft-deleted menu items.
25. Remove wait-time data from the product direction. Do not add wait-time fields to the schema, display estimated wait times, or invent wait-time values. F16/B21 may still cover promotions, delivery costs, and ratings if reliable sources are approved later.
26. Make restaurant diversity a Must requirement. After mandatory filtering and rejected-item exclusion, fill shortlist slots from distinct restaurants first; add a second item from an already represented restaurant only when needed to complete the shortlist.
27. Move GPS/current-location support to Won't have for the first release. The first release uses manual `Zone` records only; F9 remains documented for future traceability and requires separate privacy approval before implementation.
28. Use seed data for the initial administrator, minimum master data, and local/demo sample restaurant/menu data. Seed data may focus on MFU-area samples, but the product schema and code must not hardcode MFU as the only supported area; real catalog data is maintained through admin APIs/UI.
29. Allow real restaurant/menu seed data only when team-collected or otherwise authorized, with source and verification date recorded in seed evidence. Use team-owned, authorized, or generated-placeholder images only; mark unverified catalog seed rows as synthetic/sample data.
30. Interpret NFR1 as a warm API performance target. Free-tier hosting cold-start latency is measured and reported separately, not mixed into the warm p95 requirement.
31. Approve NFR2: at least 80% of at least five target-user testers must complete F1–F4 within 60 seconds without facilitator help.
32. Treat THB 50–100 as a quick-select budget option based on survey evidence, not as an automatic default. Users must choose their budget explicitly.
33. Treat any Cloudflare Pages, Koyeb API, Koyeb Postgres, or Cloudflare R2 deployment as public production. Development and verification run locally until the human explicitly approves production deployment after verification, privacy review, and deployment review.
34. Do not implement Computer Crime Act traffic-log storage yet. Block public production deployment until an accountable human/legal reviewer confirms Section 26 applicability. `AuditLog` is not a substitute; if applicable, traffic-log schema, fields, access, security, and retention require separate approval.
35. Defer self-service password reset. Do not add email delivery, reset tokens, reset endpoints, or reset screens until email ownership verification and an email provider are separately approved.
36. Allow only the environment-backed seeded administrator in the first full-app pass. Public registration always creates `USER`; do not implement additional admin creation, invitation, role promotion/demotion, manual maintenance provisioning, or admin user-management screens/APIs.
37. Do not implement administrator password change or password reset. Administrator credentials are provisioned once by the initial environment-backed seed process.
38. Defer registered-user password change. Do not add change-password endpoints or screens in the first full-app pass; revisit the workflow in a later approved scope decision.
