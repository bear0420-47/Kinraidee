# Test Plan: ให้ผู้ใช้ลองเลือกเงื่อนไขและสุ่มอาหาร Kinraidee

**ปรับปรุง:** 25 ตุลาคม 2026 · **สถานะ:** Draft · **ผล:** ยังไม่ได้ทดสอบ (Not run)

ฉบับนี้ปรับจากแผนเดิมที่มี 27 กรณี ให้เหลือ **8 งานที่ผู้ทดลองทำผ่านหน้าจอได้** ตามคำขอเจ้าของโครงการ ตัดเคสตรวจระบบเบื้องหลังออกก่อน ไม่ได้เปลี่ยนข้อกำหนดของผลิตภัณฑ์หรืออ้างว่าการตรวจส่วนที่เอาออกผ่านแล้ว

## 1. เราจะให้ผู้ทดลองลองอะไรบ้าง

| งาน | ให้ลองทำอะไร | สิ่งที่อยากรู้ |
|---|---|---|
| UAT-01 | เลือกงบ รสชาติ ประเภทอาหาร และโซน แล้วรับเมนูแนะนำ | เลือกเงื่อนไขเองได้ไหม และได้ผลตรงที่เลือกไหม |
| UAT-02 | เปิดการ์ดทีละใบและเปิดทั้งหมด | เข้าใจการเปิดการ์ดและอ่านข้อมูลอาหารได้ไหม |
| UAT-03 | เปลี่ยนเมนูที่ไม่อยากกิน | ได้เมนูอื่นที่ตรงเงื่อนไขและไม่ซ้ำไหม |
| UAT-04 | ยกเลิกการเปลี่ยนเมนูครั้งล่าสุด | เอาเมนูเดิมกลับมาได้ไหม |
| UAT-05 | เปลี่ยนเงื่อนไขแล้วหาเมนูใหม่ | แก้สิ่งที่เลือกไว้และได้ผลตามเงื่อนไขใหม่ไหม |
| UAT-06 | เลือกเมนู ลองกลับไปคิดต่อ แล้วเลือกและยืนยัน | ทำจนเลือกอาหารสำเร็จได้เองไหม |
| UAT-07 | เริ่มเลือกอาหารรอบใหม่ | เริ่มใหม่ได้โดยไม่มีคำตอบหรือเมนูจากรอบก่อนค้างไหม |
| UAT-08 | ลองเงื่อนไขที่ไม่พบเมนู แล้วหาทางเลือกต่อ | เข้าใจข้อความและใช้ข้อเสนอหรือแก้เงื่อนไขเองได้ไหม |

**ลำดับ:** ทุกคนทำ UAT-01 ถึง UAT-07 โดยมีข้อมูลให้เปลี่ยนเมนูได้ ส่วน UAT-08 ทีมต้องเตรียมเงื่อนไขที่ไม่มีผลและมีทางเลือกต่อไว้ก่อน หากเตรียมไม่ได้ให้ระบุ Not run/Blocked ไม่ให้ผู้ใช้เดาสุ่มจนเจอเอง

Google Forms ปรับ Section 3 ให้ตรงกับ UAT-01–UAT-08 แล้วเมื่อ 25 ตุลาคม 2026 งานที่ 8 แยกรอบ A และ B จึงมีชุดบันทึกผล 9 ชุด รวม 27 ช่อง (ผลสำเร็จ เวลา และปัญหา ชุดละสามช่อง) การมีคำถามในฟอร์มยังไม่ใช่หลักฐานว่าได้รันทดสอบแล้ว

## 2. ขอบเขตของรอบนี้

ทดสอบเฉพาะการเลือกอาหารแบบไม่ต้องเข้าสู่ระบบ ตั้งแต่หน้าแรกจนยืนยันเมนู รวมเส้นทางแก้เงื่อนไข เปลี่ยนเมนู และเริ่มใหม่ ผู้ทดลองไม่ต้องเปิดเครื่องมือของนักพัฒนาหรือส่งข้อมูลทดสอบด้วยตัวเอง

### เอาออกจากแผนรอบนี้ก่อน

- การยิง API, ตรวจ request/response, HTTP status, schema และ validation ที่ขอบเขต API
- การตรวจฐานข้อมูล sessionStorage และ log รวมถึงการตรวจข้อมูลที่บันทึกอยู่ภายใน
- การวัดความเร็ว API แบบ p95, cold start และทดสอบจำนวนข้อมูลมาก ๆ
- การจำลอง API ล่ม เครือข่ายล่ม ส่งคำขอซ้ำ หรือผลตอบกลับสลับลำดับ
- การทดสอบค่ารอยต่อราคาทุกค่าแบบอัตโนมัติ และการพิสูจน์อัลกอริทึมเลือกข้อเสนอที่ดีที่สุด

ส่วนนี้เป็นงานทีมพัฒนาหรือ QA และยังเป็น coverage gap ของการตรวจทั้งระบบ ไม่ใช่งานของผู้เข้าร่วมในฟอร์มนี้ การกดสุ่มแล้วเห็นว่าราคา/รส/ประเภท/โซนถูกต้องยังอยู่ในแผน เพราะเป็นผลที่ผู้ใช้เห็นโดยตรง

ไม่รวมสมัครสมาชิก บัญชี Favorites ประวัติ Admin GPS ค่าส่ง โหวตกลุ่ม การสั่งและจ่ายเงิน ส่วนปุ่มให้ระบบตัดสินใจแทนหนึ่งรายการยังไม่รวมจนกว่าจะยืนยันเส้นทางใช้งานตาม F12; ไม่ถือว่าปุ่มนี้เป็นสิ่งเดียวกับการรับการ์ดไม่เกินสามใบ

## 3. Test levels

| ระดับ | ใช้ในรอบนี้ไหม | ตรวจอะไร |
|---|---|---|
| Unit / Component | ไม่รวมในรอบผู้ใช้ | ทีมพัฒนาตรวจแยกต่างหาก |
| Integration | เอาออกก่อน | ไม่ตรวจการเชื่อมต่อและข้อมูลภายในเป็นรายจุดในเอกสารนี้ |
| System / E2E | ใช้เฉพาะหน้าจอหลัก | ดูพฤติกรรมของแอปจริงตั้งแต่เลือกเงื่อนไขจนจบ ไม่ใช่ mockup |
| UAT | ใช้กับผู้ทดลอง 10 คน | ให้ทำด้วยตัวเอง บันทึกทำได้ไหม เวลา และปัญหา แล้วตอบแบบประเมิน |

## 5. ทีมต้องเตรียมอะไร

1. เปิดแอปจริงและเช็กว่าเลือกอาหารได้ก่อนเริ่มรับผู้ทดลอง ใช้สภาพแวดล้อมทดสอบ ไม่แก้ข้อมูลจริงของผู้ใช้
2. เตรียมเมนูจำลองที่รู้ราคา รส ประเภท โซน และร้าน เพื่อใช้เทียบกับหน้าจอ ไม่ใช้ข้อมูลผู้เข้าร่วมเป็น fixture
3. ชุดปกติต้องมีเมนูตรงเงื่อนไขอย่างน้อย 4 รายการและอย่างน้อย 3 ร้าน เพื่อให้รับสามใบและเปลี่ยนได้อีกหนึ่งรายการ
4. ตัวอย่างชุดปกติ: งบ 50–100 บาท / รสเผ็ด / ข้าว / โซน A มีเมนูราคา 60, 70, 80, 90 บาทจากคนละร้าน เมนูผิดงบ ผิดรส ผิดประเภท หรือผิดโซนต้องไม่ปรากฏ
5. เตรียมอีกชุดสำหรับ UAT-05 ให้แก้เป็นเงื่อนไขใหม่แล้วมีผล และชุด UAT-08 ที่เงื่อนไขเดิมไม่มีผล แต่เงื่อนไขที่ระบบเสนอมีเมนูให้เลือกจริง
6. เตรียมคนอ่านโจทย์และคนจดผล/จับเวลา โดยไม่แนะนำว่าต้องกดปุ่มไหน
7. ใช้ [Consent form](participant-consent-form.md) ก่อนเริ่มเก็บข้อมูล แล้วตอบคำถามก่อนใช้ใน [UTAUT2.md](UTAUT2.md) จากนั้นลองใช้งานและตอบส่วนหลังใช้ การถามวิธีเดิมไม่ใช่การจับเวลาเปรียบเทียบก่อน–หลังจริง

## 6. รายละเอียดงานสำหรับผู้ทดลอง

อ่านให้ผู้ทดลองฟังว่า “เรากำลังทดสอบแอป ไม่ได้ทดสอบความสามารถของคุณ ถ้าทำไม่ได้หรือติดปัญหา บอกได้เลย” ให้โจทย์ทีละงาน ไม่อ่านผลที่คาดหวังหรือเฉลยปุ่มล่วงหน้า

### UAT-01 — เลือกเงื่อนไขและรับเมนู

- **เริ่มจาก:** หน้าแรก ผู้ใช้ไม่ได้เข้าสู่ระบบ มีชุดข้อมูลปกติพร้อม
- **โจทย์:** “คุณกำลังเลือกอาหารมื้อหนึ่ง มีงบ 50–100 บาท เลือกรสชาติ ประเภทอาหาร และโซนตามที่ตกลงไว้ แล้วหาเมนูที่เหมาะกับมื้อนี้”
- **ควรได้:** ทำได้โดยไม่สมัคร เลือกตามลำดับงบ → รส → ประเภท → โซน ไม่มีตัวเลือกถูกเลือกแทนตั้งแต่เริ่มใหม่ เห็นสรุปเงื่อนไขและการ์ดไม่เกินสามใบ
- **ทีมจดเพิ่ม:** เงื่อนไขที่เลือกไว้ เพื่อเทียบกับเมนูหลังเปิดการ์ด
- **จับเวลา:** เริ่มจาก Home จนเห็นการ์ด หรือหยุดทำ
- **อ้างอิง:** F1, F2, F6; P1, P2, P5–P8; B1, B2, B6

### UAT-02 — เปิดการ์ดและอ่านเมนู

- **เริ่มจาก:** การ์ดคว่ำที่ได้จาก UAT-01
- **โจทย์:** “ลองดูว่ามีเมนูอะไรบ้าง เริ่มดูหนึ่งใบ แล้วดูเมนูที่เหลือให้ครบ”
- **ควรได้:** เปิดทีละใบและเปิดทั้งหมดได้ เห็นชื่อเมนู ร้าน ราคา โซน และเหตุผลแนะนำที่ตรงกับข้อมูลทดสอบ เมนูทุกใบตรงเงื่อนไข ไม่เกิดผลใหม่เพียงเพราะเปิดการ์ด เมื่อข้อมูลมีร้านเพียงพอ เมนูในรอบนั้นมาจากต่างร้าน
- **ทีมจดเพิ่ม:** ราคา/เงื่อนไขที่ผิด และข้อมูลที่ผู้ใช้หาไม่เจอ ไม่ต้องตรวจการทำงานภายใน
- **จับเวลา:** จากการ์ดคว่ำจนดูครบ หรือหยุดทำ
- **อ้างอิง:** F2, F3, F19, NFR3, NFR8; P3, P5–P8; B2, B3, B24; journey

### UAT-03 — เปลี่ยนเมนูที่ไม่อยากกิน

- **เริ่มจาก:** มีการ์ดเปิด และมีเมนูอื่นที่ตรงเงื่อนไขเหลืออยู่
- **โจทย์:** “สมมติว่ามีหนึ่งเมนูที่คุณไม่อยากกิน ลองหาเมนูอื่นมาแทน โดยใช้เงื่อนไขเดิม”
- **ควรได้:** ได้เมนูอื่นแทนช่องเดิม โดยเริ่มเป็นการ์ดคว่ำ เปิดดูแล้วไม่ซ้ำเมนูที่เพิ่งปฏิเสธหรือใบอื่นที่ยังอยู่ และยังตรงเงื่อนไขเดิม
- **จับเวลา:** จากเริ่มเปลี่ยนตัวเลือกจนเห็นรายละเอียดเมนูใหม่ หรือหยุดทำ
- **อ้างอิง:** F4, F5, NFR9; P3, P4; B4, B5; journey

### UAT-04 — เอาเมนูเดิมกลับมา

- **เริ่มจาก:** เพิ่งเปลี่ยนเมนูใน UAT-03 และยังมีตัวเลือกเลิกทำ
- **โจทย์:** “ตอนนี้เปลี่ยนใจ อยากได้เมนูที่เพิ่งเปลี่ยนออกไปกลับมา ลองเอากลับมาให้เหมือนเดิม”
- **ควรได้:** คืนเมนูเดิมในช่องเดิมและสถานะเปิด/คว่ำเดิม เมนูแทนถูกเอาออก ไม่ต้องกลับไปเริ่มเลือกเงื่อนไขใหม่
- **จับเวลา:** จากเริ่มโจทย์จนคืนเมนูได้ หรือหยุดทำ
- **อ้างอิง:** F4, F5; B4, B5; journey เรื่อง “เลิกทำ”

### UAT-05 — เปลี่ยนเงื่อนไข

- **เริ่มจาก:** มีเงื่อนไขที่เลือกไว้และมีชุดข้อมูลสำหรับเงื่อนไขใหม่
- **โจทย์:** “ตอนนี้คุณอยากเปลี่ยนประเภทอาหารจากเดิมเป็นอีกประเภทหนึ่งตามที่ตกลงไว้ แต่ยังใช้งบและโซนเดิม ลองหาตัวเลือกใหม่”
- **ควรได้:** แก้เงื่อนไขได้โดยไม่สมัคร หน้าสรุปและเมนูรอบใหม่ตรงกับค่าที่เปลี่ยน ส่วนค่าที่ผู้ใช้ไม่ได้แก้ยังตรงความตั้งใจ ไม่เงียบ ๆ เปลี่ยนงบหรือโซนเอง
- **จับเวลา:** จากเริ่มแก้เงื่อนไขจนเห็นผลรอบใหม่ หรือหยุดทำ
- **อ้างอิง:** F1, F2, F7, NFR8; P1, P2, P6; B1, B2, B7

### UAT-06 — เลือกเมนูและยืนยัน

- **เริ่มจาก:** มีเมนูเปิดให้เลือก
- **โจทย์:** “เลือกเมนูหนึ่งที่สนใจ ลองกลับไปคิดต่อก่อนหนึ่งครั้ง แล้วเลือกเมนูที่ต้องการและยืนยันให้เสร็จ”
- **ควรได้:** ดูรายละเอียดได้ กลับไปคิดต่อแล้วกลับสู่การ์ดเดิมได้ และยืนยันจนเห็นว่าเลือกสำเร็จ เมนูที่ยืนยันตรงกับที่เลือก ไม่บังคับเปิดครบทุกใบก่อนเลือก
- **จับเวลา:** จากเริ่มเลือกเมนูจนยืนยันสำเร็จ หรือหยุดทำ
- **อ้างอิง:** F3, F6, F7; P1, P4; B3, B6, B7; journey

### UAT-07 — เริ่มรอบใหม่

- **เริ่มจาก:** ยืนยันสำเร็จจาก UAT-06
- **โจทย์:** “เลือกมื้อนี้เสร็จแล้ว ลองเริ่มเลือกอาหารสำหรับมื้อใหม่อีกครั้ง”
- **ควรได้:** กลับหน้าแรกและเริ่มคำถามแรกได้ ไม่มีคำตอบ การ์ด หรือการเปลี่ยนเมนูจากรอบก่อนค้าง หากทดสอบปุ่มเริ่มใหม่บนหน้าการ์ดให้แยกรอบย่อย และระบุว่าทดสอบเส้นทางไหน
- **จับเวลา:** จากเริ่มรอบใหม่จนเห็นคำถามแรกที่ยังไม่มีคำตอบ หรือหยุดทำ
- **อ้างอิง:** F7; P1, P2; B7; journey

### UAT-08 — ไม่พบเมนูตรงเงื่อนไข

- **เริ่มจาก:** ทีมให้ชุดเงื่อนไขที่เตรียมไว้ว่าไม่พบผล แต่มีข้อเสนอที่ให้เมนูได้จริง เป็นคนละรอบจากชุดปกติ
- **โจทย์รอบ A:** “ใช้เงื่อนไขชุดนี้หาอาหาร ถ้าไม่มีเมนูตรง ให้ลองใช้ทางเลือกที่แอปเสนอเพื่อหาเมนูต่อ”
- **โจทย์รอบ B:** “กลับมาที่เงื่อนไขเดิมที่ไม่มีผล คราวนี้ลองแก้เงื่อนไขเองตามชุดใหม่ที่ตกลงกันไว้”
- **ควรได้:** บอกว่าไม่พบผล ไม่แสดงเมนูผิดเงื่อนไขแทน ข้อเสนออธิบายว่าจะเปลี่ยนอะไร ผู้ใช้เป็นคนยอมรับก่อนและได้เมนูตามเงื่อนไขใหม่ ส่วนแก้เองกลับไปเห็นเงื่อนไขเดิมและแก้ต่อได้
- **จับเวลา:** แยกรอบ A และ B ตั้งแต่เห็นข้อความไม่พบผลจนมีเมนูใหม่ หรือหยุดทำ
- **ข้อจำกัด:** ไม่ตรวจวิธีคำนวณหรืออันดับข้อเสนอภายใน หากชุดข้อมูลไม่มีข้อเสนอ ต้องบันทึกและไม่แสร้งว่าได้ทดสอบเส้นทางยอมรับข้อเสนอแล้ว
- **อ้างอิง:** F1, F2, F7, UC1, NFR8; P1, P4; B1, B2, B7; journey

## 7. ช่องบันทึกผลที่ควรมีในฟอร์ม

แต่ละงานใช้สามคำถามเหมือนกัน:

1. **ทำเสร็จไหม?** — ทำเสร็จเอง / ทำเสร็จแต่มีคนช่วย / ทำไม่เสร็จ / ยังไม่ได้ลอง
2. **ใช้กี่วินาที?** — คำตอบสั้น ใส่เฉพาะตัวเลข หากไม่ได้จับเวลาให้เว้น ไม่กรอก 0 แทน และถ้าหยุดก่อนเสร็จให้จดเวลาถึงจุดหยุดโดยผูกกับสถานะทำไม่เสร็จ
3. **เจอปัญหาอะไรบ้าง? ถ้ามีคนช่วย ช่วยตรงไหน?** — คำตอบสั้น ถ้าไม่มีให้พิมพ์ “ไม่มี”

คนจับเวลาหยุดก่อนให้กรอกฟอร์ม ไม่รวมเวลาพิมพ์คำตอบกับเวลาทำงาน UAT-08 มีสองรอบให้บันทึก A/B แยกกัน ทีมต้องตรวจผลที่เห็นจริงด้วย เพราะผู้ใช้อาจคิดว่าทำเสร็จทั้งที่ได้อาหารผิดเงื่อนไข

| รหัสผู้ใช้ | งาน/รอบย่อย | ทำเสร็จไหม (ผู้ใช้ตอบ) | เวลา (วินาที) | ทีมตรวจว่าได้ผลถูกต้องไหม | ปัญหา/การช่วยเหลือ | สถานะรัน |
|---|---|---|---|---|---|---|
| U01–U10 (แยกแถวจริงต่อคนต่องาน) | UAT-01–UAT-08 | — | — | — | — | Not run |

ไม่เอางานที่ยังไม่ได้ลองมานับเป็นสำเร็จ ไม่คิดค่าเฉลี่ยเวลาของงานที่ล้มเหลวปนกับเวลาเสร็จจริง รายงานจำนวนที่ทำเสร็จเอง/ต้องช่วย/ทำไม่เสร็จ/ไม่ได้ลองแยกกัน และรายงานจำนวนข้อมูลที่ใช้คำนวณ

## 8. ขั้นตอนต่อคน

**Consent → คำถามก่อนใช้ → งานทดสอบทีละงาน → คำถาม UTAUT2 หลังใช้ → คำถามเสริมหลังใช้ตาม pain point**

ให้ผู้ใช้ลองเอง ไม่จับเมาส์หรือชี้ปุ่มแทน หากต้องช่วยให้บันทึกไว้ ถ้าพบว่าเลือกอาหารผิดเงื่อนไขหรือไปต่อไม่ได้ ให้จดปัญหา ไม่เปลี่ยนผลเป็นผ่านเพื่อให้ทดสอบต่อได้

คำถามก่อน–หลังและคะแนนคำนวณใช้ฉบับปัจจุบันใน [UTAUT2.md](UTAUT2.md) ไม่คัดรายการรหัสคำถามเก่ามาซ้ำ เพราะเวอร์ชันและบางข้อเปลี่ยนไปแล้ว

การจับเวลาในงานเหล่านี้เป็นเวลาทำงานผ่านหน้าจอจริง ส่วนคำถามก่อนใช้เรื่อง “ปกติใช้กี่นาที” เป็นความจำของผู้ตอบ จึงห้ามนำมาอ้างเป็นผล before/after ที่จับเวลาจริง

## 9. เกณฑ์สรุปและข้อจำกัด

- ทีมตรวจว่าผลตรงเงื่อนไขทุกใบ (NFR8), ไม่เกินสามใบ (NFR3), เปลี่ยนแล้วไม่ซ้ำเมื่อมีตัวเลือกเหลือ (NFR9) และผู้ใช้เลือกจนสำเร็จได้ ผลผิดเงื่อนไขถือเป็นปัญหาของระบบแม้ผู้ใช้บอกว่าทำเสร็จ
- ไม่สรุปจากคะแนน UTAUT2 ว่าฟังก์ชันผ่าน และไม่อ้างว่าได้ตรวจระบบทั้งแอปจากการทดสอบเฉพาะหน้าจอนี้
- NFR2 เดิมระบุผู้ใช้ขั้นต่ำห้าคน อย่างน้อย 80% จบ F1–F4 ภายใน 60 วินาทีโดยไม่ช่วย งานที่แบ่งกรอกทีละข้อมีช่วงพัก จึงไม่ใช้ผลรวมเวลาหรือเวลาที่ผู้ใช้เดามาอ้างว่าผ่าน NFR2 ต้องมีรอบจับเวลาต่อเนื่องและยืนยันจุดเริ่ม/จุดจบก่อนหากจะตัดสินเกณฑ์นี้
- งานที่ทำไม่ได้เพราะชุดข้อมูลไม่พร้อมให้เป็น Blocked; งานที่ยังไม่ทำเป็น Not run ไม่ใช่ Pass
- เรื่องภาพ/ข้อความตอนตัวแทนหมด ขอบช่วงงบที่กำกวม และเส้นทางแก้เงื่อนไขที่ยังไม่ชัด ให้ทีมตรวจเอกสารและยืนยันก่อนตัดสิน ไม่ใช้แอปที่ทำอยู่เป็นคำตอบแทน requirement
- รายการทดสอบเบื้องหลังที่เอาออกยังต้องมีหลักฐานแยกก่อนขออนุมัติปล่อยระบบ บันทึกผลจริงที่ไม่ระบุตัวบุคคลใน docs/verification.md ตามกติกาโปรเจกต์ ห้ามสร้างผลทดสอบขึ้นเอง
