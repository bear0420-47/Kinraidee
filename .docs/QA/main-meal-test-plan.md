# Test Plan: เลือกเงื่อนไขและสุ่มอาหาร Kinraidee

**วันที่:** 2026-10-21 · **สถานะ:** Draft · **ผลการทดสอบ:** Not run ทุกกรณี

เอกสารนี้เป็นแผนทดสอบระบบหลัก ตั้งแต่เลือกเงื่อนไขก่อนสุ่ม ไปจนถึงเลือกและยืนยันเมนู ยังไม่ได้รันแอปหรือดำเนินการทดสอบตามแผนนี้ และไม่เปลี่ยนสถานะการอนุมัติข้อกำหนดเดิม

### กำหนดวันทดสอบ

| รอบ | วันและวันที่ | เวลา (Asia/Bangkok) | กิจกรรม |
|---|---|---|---|
| รอบที่ 1 | วันอังคารที่ 27 ตุลาคม 2026 | 15:00–17:00 น. | ทดสอบฟังก์ชันหลักแบบ hands-off และตอบ UTAUT2 หลังใช้ |
| รอบที่ 2 | วันพุธที่ 28 ตุลาคม 2026 | เริ่ม 10:00 น.; ยังไม่กำหนดเวลาสิ้นสุด | ทดสอบผู้ที่ยังไม่ครบ และ/หรือทดสอบซ้ำจุดที่มีปัญหา ตามการจัดสรรรายชื่อก่อนเริ่ม |

เป้าหมายผู้ทดสอบนอกทีม **10 คนที่ไม่ซ้ำกัน** ทั้งสองวันรวมกัน แบ่งเป็นวันอังคาร U01–U05 จำนวน 5 คน และวันพุธ U06–U10 จำนวน 5 คน (ยืนยันการแบ่งรอบ 2026-10-22) การทดสอบซ้ำคนเดิมไม่ถือเป็นผู้เข้าร่วมใหม่ และต้องแยกผลครั้งแรกออกจาก retest

**ประเมินเวลาเบื้องต้น:** หากทดสอบทีละคน เสนอประมาณคนละ 10–12 นาที รวมอ่าน consent, ทดลอง, ตอบแบบสอบถาม และเปลี่ยนผู้ทดสอบ สิบคนใช้ประมาณ 100–120 นาที วันอังคารจึงค่อนข้างแน่นและควรเผื่อวันพุธสำหรับคนที่เหลือ/ปัญหาเทคนิค เวลานี้เป็นประมาณการจัดงาน ไม่ใช่เกณฑ์ 60 วินาทีของ NFR2 ให้ลอง pilot ก่อนและยืนยันเวลาสิ้นสุดวันพุธอีกครั้ง

ทีมเตรียมระบบและตรวจ smoke/integration ก่อนเวลาเริ่มรับผู้ทดสอบ ไม่ให้ผู้ใช้ทั้งสิบคนต้องทำทุกกรณีทางเทคนิคทั้ง 27 รายการ

## 1. เป้าหมาย

ตรวจว่าผู้ใช้ที่ไม่รู้จะกินอะไรสามารถกรอกเงื่อนไขสั้น ๆ รับตัวเลือกที่ตรงความต้องการ เปลี่ยนตัวเลือกที่ไม่ถูกใจ และเลือกอาหารจบด้วยตัวเองได้ โดยไม่ต้องสมัครสมาชิก

คำว่า “สุ่มอาหาร” ในแผนนี้หมายถึง workflow **Get a meal shortlist**: ระบบกรองเงื่อนไขก่อนให้ตัวเลือกไม่เกินสามรายการ การเปิดการ์ดเป็นการเปิดดูผลที่เลือกมาแล้ว ไม่ใช่สุ่มข้อมูลใหม่ทุกครั้ง

## 4. ขอบเขต

### ทดสอบในรอบนี้

**ขอบเขตสำหรับผู้ใช้สิบคนในวันนัด:** ทดสอบเฉพาะฟังก์ชันหลักที่กำหนด คือ **เลือกงบ/รสชาติ/ประเภทอาหาร/โซน → สุ่ม → เปิดการ์ด → เปลี่ยนเมนู → เลือกและยืนยัน** แล้วตอบ UTAUT2 คะแนน 1–5 ไม่รวมการสมัครสมาชิก ระบบ Admin หรือฟังก์ชันอื่นของแอป

รายการด้านล่างยังเป็นขอบเขต QA ของ main workflow โดยแยกงานเตรียมของทีมออกจากภารกิจที่ผู้เข้าร่วมต้องทำ:

- หน้าเริ่มใช้งานแบบไม่เข้าสู่ระบบ
- การเลือก **งบ → รสชาติ → ประเภทอาหาร → โซน** และการตรวจค่าก่อนส่ง
- หน้าสรุปเงื่อนไข การกด `สับการ์ดเมนู` และผลลัพธ์จาก API/ฐานข้อมูลจริง
- การเปิดการ์ดทีละใบหรือเปิดทั้งหมด ข้อมูลบนการ์ด และการกระจายตัวเลือกข้ามร้าน
- การเปลี่ยนเมนู ไม่ให้ซ้ำ การเลิกทำ และกรณีไม่มีเมนูเหลือ
- การไม่พบเมนู การยอมรับข้อเสนอเปลี่ยนเงื่อนไข และการแก้เอง
- การเลือกเมนู ย้อนกลับไปคิดต่อ ยืนยัน เริ่มใหม่ และกลับมาทำ flow ที่ยังไม่จบ
- การใช้คีย์บอร์ด การทดสอบ hands-off ประสิทธิภาพ API และความเป็นส่วนตัวเฉพาะ flow นี้

| ใครทำ / เมื่อไหร่ | ขอบเขตที่ใช้จริง | Case ที่เกี่ยวข้อง |
|---|---|---|
| ทีม QA ก่อนวันนัด | ตรวจเงื่อนไข ผลกรอง จำนวนและข้อมูลเมนู การเปิดการ์ด ความไม่ซ้ำ และการยืนยัน | MAIN-01–06, MAIN-09–12, MAIN-14, MAIN-20 |
| ผู้เข้าร่วมสิบคนในวันนัด | Hands-off flow หลักตามโจทย์เดียวกัน แล้วตอบ UTAUT2 | MAIN-24 โดยสังเกตพฤติกรรมจาก MAIN-01–06, MAIN-09–12, MAIN-14, MAIN-20; แบบสอบถามหัวข้อ 10.1 |
| ทีม QA แยกจากช่วงผู้ใช้ | ขอบเขตงบ/ค่าผิด, no-match, undo, เริ่มใหม่, keyboard, performance, privacy และ network error | MAIN-07–08, MAIN-13, MAIN-15–16, MAIN-18–19, MAIN-21–23, MAIN-25–27 |
| ยังไม่รวมในการนัดผู้ใช้ครั้งนี้ | Decide for me ซึ่งยังต้องชี้แจง interaction | MAIN-17 เป็น Partial coverage ตาม Q5 |

การเก็บเคสสนับสนุนไว้ไม่ใช่การเพิ่มฟังก์ชันให้ผู้ใช้ทดสอบ หากทีมยังไม่ได้ทำ ให้คงสถานะ Not run และระบุ coverage gap ไม่สรุปว่ารอบผู้ใช้ครอบคลุมทุกเคสหรือทุก NFR แล้ว

### ยังไม่ครอบคลุม

- สมัคร/เข้าสู่ระบบ Favorites ประวัติ การตั้งค่าเริ่มต้น และ Admin CRUD เต็มรูปแบบ
- GPS/ระยะทาง อาหารแพ้ โปรไฟล์สุขภาพ โหวตกลุ่ม ค่าส่ง โปรโมชั่น รีวิว การสั่งหรือจ่ายเงิน
- การพิสูจน์ว่าการสุ่มกระจายเท่ากัน เพราะยังไม่มีข้อกำหนดความน่าจะเป็น
- Refresh test แบบเพิ่ม record แล้วตรวจฐานข้อมูล เป็นคนละแผนกับ core flow นี้ เงื่อนไขและการ์ดใน session ไม่ใช่หลักฐาน database persistence
- การรับรองกฎหมายทั้งหมด: LR10–LR12 เรื่อง traffic log ยังขึ้นกับการตัดสิน applicability ของผู้รับผิดชอบ ไม่ตัดสินแทนในแผนนี้; การยินยอม/ข้อตกลงตาม LR14–LR16 และ NFR11 ทดสอบแยกเมื่อเปิดใช้

## 6. วิธีและลำดับทดสอบ

### 6.1 Test levels — ทดสอบระดับไหนบ้าง

เดิมเอกสารมีคำว่า Integration และ End-to-end ในรายการ แต่ยังไม่มีหัวข้อ Test levels แยกชัดเจน ตารางนี้กำหนดระดับการทดสอบสำหรับรอบนี้ โดยไม่อ้างว่าดำเนินการแล้ว

| Test level | หมายถึงอะไร | ใช้กับแผนนี้อย่างไร | ใครทำ / เคสตัวอย่าง |
|---|---|---|---|
| Unit / Component testing | ตรวจฟังก์ชันหรือ component แยกชิ้น | ไม่ใช่กิจกรรมของผู้เข้าร่วมสิบคน; ใช้ผลทดสอบของทีมพัฒนาเป็นหลักฐานสนับสนุนแยก ไม่ถือว่าผ่านจากการทำ hands-off | ทีมพัฒนา; ไม่มี unit case เพิ่มในเอกสารนี้ |
| Integration testing | ตรวจว่าส่วนต่าง ๆ ส่งข้อมูลและทำงานร่วมกันถูกต้อง | ตรวจ Web → API → PostgreSQL ว่าเงื่อนไขที่ส่งตรงกับผลที่แสดง และเปลี่ยนเมนูได้ถูกต้อง | ทีม QA ก่อนวันนัด; MAIN-06, MAIN-10, MAIN-14, MAIN-26 |
| System testing | ตรวจแอปที่รวมส่วนต่าง ๆ แล้ว ตั้งแต่ต้นจนจบ | ตรวจ main workflow รวมกรณีปกติและกรณีผิดพลาด โดยไม่ขยายไปทั้งแอป | ทีม QA; MAIN-01–23, MAIN-25–27 ตาม scope และข้อจำกัดแต่ละเคส |
| Acceptance testing (UAT) | ให้กลุ่มผู้ใช้จริงลองทำงานเพื่อประเมินว่าตอบโจทย์การใช้งานหรือไม่ | ผู้ใช้นอกทีมสิบคนทำ hands-off เลือกเงื่อนไขจนยืนยัน; บันทึกความสำเร็จ เวลา และการช่วยเหลือ โดยผู้รับผิดชอบเป็นผู้ตัดสินรับงาน | ผู้เข้าร่วม; MAIN-24 วันที่ 27–28 ตุลาคม 2026 |

**แยกระดับออกจากวิธี:** Hands-off เป็นวิธีดำเนินการทดสอบ ส่วน functional, usability, performance และ privacy เป็นประเภท/มุมการตรวจ UTAUT2 เป็นแบบประเมินการยอมรับหลังใช้ ไม่ใช่ Test level เพิ่มอีกระดับ และไม่แทนผล functional test

### 6.2 ลำดับดำเนินการ

1. **Smoke:** MAIN-01, MAIN-06, MAIN-12, MAIN-20 ด้วยระบบจริง หาก flow หลักไปต่อไม่ได้ให้หยุด hands-off
2. **Functional/Integration:** ทดสอบตัวกรอง จำนวนผล ข้อมูลบนการ์ด ความหลากหลาย และสถานะการ์ด เทียบ API กับ fixture
3. **Negative/Boundary/State:** ทดสอบค่าผิด ไม่มีผล การเปลี่ยนเมนู เลิกทำ เริ่มใหม่ และผลขอบเขตงบ
4. **Quality:** ทดสอบ keyboard, API performance, privacy และสถานการณ์ขัดข้องที่ระบุว่า exploratory
5. **Hands-off:** ผู้ใช้นอกทีมทำ workflow เอง เก็บเวลาและการช่วยเหลือ
6. **ประเมินหลังใช้:** ให้ผู้ใช้ตอบ UTAUT2-based คะแนน 1–5 ตามหัวข้อ 10.1 เก็บคะแนนไว้คำนวณแยกจากผล Pass/Fail และเวลา
7. **Regression:** หลังแก้ defect รันเคสที่เคย Fail และส่วนที่ได้รับผลกระทบ รวม smoke ใหม่

ตารางต่อไปนี้เป็นรายการทดสอบระดับแผน มีข้อมูลเริ่มต้น วิธีทำ และผลที่คาดหวังเพื่อแตกเป็น executable cases ต่อได้ ทุกแถวเริ่ม **Not run**

**ลำดับทดสอบ H/M** เป็นข้อเสนอของ QA: H = ตรวจต้นรอบเพราะอาจทำให้เลือกผิดหรือจบ flow ไม่ได้, M = ตรวจหลัง flow หลัก ลำดับนี้ไม่เปลี่ยน MoSCoW ในสเปก: F1–F7/F19 เป็น Must, F12 เป็น Should; NFR ไม่มี MoSCoW ระบุแยก

### 10.1 แบบประเมินหลังทดลองใช้ — UTAUT2-based คะแนน 1–5

หลังผู้ใช้ยืนยันเมนูเสร็จ หรือหยุดทดลองเพราะติดปัญหา ให้หยุดจับเวลาก่อน แล้วให้ตอบแบบสอบถามใน [UTAUT2.md](UTAUT2.md) โดยอิงเฉพาะส่วนที่ได้ทดลอง ไม่เก็บเฉพาะคนที่ทำสำเร็จ เพราะจะทำให้ขาดความคิดเห็นจากคนที่พบปัญหา

**Flow ของผู้ใช้:** ทดลองเลือกเงื่อนไขและสุ่มอาหาร → เลือก/ยืนยันหรือหยุดทดลอง → ตอบแบบประเมิน → ทีมรวบรวมคะแนนไปคำนวณภายหลัง

| คะแนน | ความหมาย |
|---|---|
| 1 | ไม่เห็นด้วยอย่างยิ่ง |
| 2 | ไม่เห็นด้วย |
| 3 | กลาง ๆ |
| 4 | เห็นด้วย |
| 5 | เห็นด้วยอย่างยิ่ง |

ใช้ “ไม่ได้ทดลอง / ประเมินไม่ได้” แยกจากคะแนน ไม่แทนเป็น 0 หรือ 3

| ชุดคำถามจาก UTAUT2.md | ใช้ดูอะไรหลังทดสอบ main workflow |
|---|---|
| PE1–PE4 | ช่วยเลือกอาหาร เร็วขึ้น และลดความพยายามในการคิดไหม |

| HM1–HM3 | การเลือกและเปิดการ์ดสนุกหรือเพลิดเพลินไหม |
| FC1–FC4 | มีอุปกรณ์ อินเทอร์เน็ต ความรู้ และความช่วยเหลือพร้อมไหม |

**วิธีเก็บและคำนวณภายหลัง:**

1. ใช้รหัสผู้ตอบเดียวกับ hands-off บันทึกเวอร์ชันแบบสอบถามและระบุว่าเป็นมาตราส่วน 1–5 เก็บคำตอบรายข้อในแหล่งข้อมูลที่จำกัดสิทธิ ไม่ commit คำตอบดิบลง repository
2. คำนวณค่าเฉลี่ยรายคนแยก PE, EE, HM, FC, SI และ BI เช่น PE = (PE1 + PE2 + PE3 + PE4) / 4; ได้ 4, 5, 4, 5 → PE = 4.50/5
3. ถ้าขาดคำตอบในด้านใด ไม่คำนวณคะแนนรวมนั้นตามกติกาใน UTAUT2.md และรายงานจำนวนผู้ตอบที่ใช้ได้ แต่อ่านคำตอบรายข้อที่มีได้
4. หาค่าเฉลี่ยกลุ่มและ SD แยกด้าน รายงาน PP1–PP7 และ SAT1 แยกรายข้อ ไม่รวมทั้งหมดเป็นคะแนน UTAUT2 ตัวเดียว
5. สรุปคู่กับผลทดสอบจริง เช่น ใช้เองจบกี่คน ใช้เวลากี่วินาที และคะแนน PE/EE/BI เป็นอย่างไร คะแนนสูงไม่ชดเชย functional test ที่ Fail

รอบนี้ยังไม่วัด Habit จากการใช้ครั้งเดียว ไม่ใช้ราคาอาหารแทน Price Value และยังไม่อ้างความตั้งใจใช้เป็นการใช้จริง ดูเงื่อนไขติดตามใน UTAUT2.md ไม่มีคะแนนผ่าน UTAUT2 ทางการกำหนดในแผนนี้

## 11. เกณฑ์สรุปรอบทดสอบ

**เกณฑ์ที่มีในข้อกำหนด:** ผลทุกตัวตรง mandatory filters (NFR8), ไม่เกินสามรายการ (NFR3), ไม่วนตัวปฏิเสธเมื่อมีตัวอื่น (NFR9), keyboard ไม่ติดขั้นตอน (NFR12), warm p95 ตาม NFR1, hands-off ตาม NFR2 และ log ต้องไม่มีข้อมูลต้องห้ามตาม NFR6

**ข้อเสนอสำหรับปิดรอบ QA นี้:** เคส H ที่มี expected result ชัดเจนต้อง Pass ทั้งหมด ไม่มี defect ค้างที่ทำให้เลือกผิดเงื่อนไข/จบ flow ไม่ได้/ข้อมูลรั่ว ส่วนเคส M และ exploratory ต้องมีผลและข้อจำกัดบันทึก หากยัง Blocked หรือ Partial ให้ระบุว่า scope ใดยังสรุปไม่ได้ ผู้รับผิดชอบยืนยันเกณฑ์ปิดรอบก่อนเริ่มใช้ ไม่ถือเป็น requirement ใหม่ที่อนุมัติแล้ว

นี่เป็นแผนเฉพาะ main workflow ไม่ใช่ release approval ก่อนขอ phase gate ต้องทำ `/audit-backlog` และ `/audit-design` ตาม AGENTS.md และก่อนรายงาน implementation เสร็จต้องบันทึก build/test/lint และ checks ที่แผนกำหนดใน `docs/verification.md` การเขียนแผนนี้ไม่ใช่การทำ gate หรืออนุมัติ deploy

## 12. การบันทึกผลและแจ้ง defect

บันทึกผลรันจริงและข้อสรุปใน [docs/verification.md](../../docs/verification.md) โดยระบุขอบเขตนี้ เก็บไฟล์หลักฐานที่ไม่ระบุตัวบุคคลในตำแหน่งที่อ้างจากผลรัน ไม่เปลี่ยน Not run เป็น Pass ก่อนทดสอบจริง

| Run ID / วันที่ | Commit / Environment | Case ID | Fixture / Conditions | Expected | Actual | Status | Evidence / Defect |
|---|---|---|---|---|---|---|---|
| ยังไม่รัน | — | — | — | — | — | Not run | — |

สถานะที่ใช้: **Not run / Pass / Fail / Blocked**; ใช้ **Partial coverage** เป็นข้อจำกัดการครอบคลุมแยกจากผลรัน

เมื่อพบ bug ให้ระบุ case และ requirement, ขั้นตอนทำซ้ำ, เงื่อนไขที่เลือก, ID เมนูจำลอง, สิ่งที่ควรได้/สิ่งที่เกิดจริง, browser/build และภาพหรือ response ที่ลบข้อมูลลับแล้ว หลังแก้ให้บันทึกผล retest และ regression ไม่แก้ expected result เพียงเพื่อให้ตรงกับแอป
